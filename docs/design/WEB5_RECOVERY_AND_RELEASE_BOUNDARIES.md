## 1. Three distinct authorities and lifecycle

- **Draft:** local actor+database epoch-scoped IndexedDB raw/lookup/lines, edit revision and optionally pending immutable intent. A transaction-complete IDB snapshot can recover after reload; not the SQL business source. Existing `drafts`/`operations` stores are separate from Dockview layout-v3 descriptors. Never store auth credentials/permissions.
- **Original immutable operation:** GUIDv4, frozen original request route/body/version/method/target, canonical rehash/fingerprint, actor+epoch and client draft checkpoint. Persist draft + intent atomically before dispatch; `DISPATCHED` means "potentially dispatched", not "SQL executed".
- **Authoritative result:** server original COMMITTED outcome or server durable terminal-negative certificate, each bound to exact immutable operation identity, current auth/permission/epoch/generation and local edit revision. A 404, status timeout, generic 409, expired bytes or search result is **neither** proof.

## 2. Client state transition table

| Current | New evidence | Safe action |
|---|---|---|
| Editable local draft | successful IDB snapshot | Mark locally durable only; still not SQL Save |
| Prepared intent awaiting dispatch | IDB transaction completed | Dispatch once; if scope changes, UNKNOWN, never new key |
| UNKNOWN | original authenticated COMMITTED result + exact matching identity | Atomically SETTLED local then apply original server IDs/version/Posted/Inventory invalidation |
| UNKNOWN | COMMITTED metadata but result expired/missing version | Keep protected; show operator case, no Edit unlock |
| UNKNOWN | 404/403/timeout/stale epoch/malformed certificate | Keep UNKNOWN; no auto resend, no clean/discard bypass |
| UNKNOWN | **verified durable NOT_EXECUTED certificate** from B02 new versioned contract | Atomically store terminal disposition and release ONLY matching local intent with CAS; preserve raw draft for explicit review |
| UNKNOWN | no B02 proof or missing matching actor/permission | Keep UNKNOWN and operator metadata, regardless of operator/UI assumptions |
| Verified negative draft | current authorized fresh baseline and review | Offer **new explicit user intent** with new GUID (not automatic replay) |
| UNKNOWN still in permitted key window | B01 crash and B02 proof + separate Owner approval for manual resend | Optional explicitly confirmed **same GUID + byte-equivalent frozen request**, one send only; otherwise UI remains disabled |

The negative certificate cannot contain a fabricated server result/version/line ID, cannot be accepted from localStorage/IndexedDB alone and must be read again under current authority. For an existing document, baseline/version must be refetched and reconciled before new mutation. Same-key resend does NOT become safe merely because 404 indicates absent journal; it relies on server serialization, expiry/tombstone and current actor rights. Existing WEB4 stores `DISPATCHED`, `SETTLED`, `REJECTED`; introduce compatible explicit negative-terminal state/version only through narrow schema-migration/CAS review, not by aliasing `REJECTED`.

## 3. Versioned HTTP and client trust boundary

Backend `2d72700294227ef69f1a7a61a2969a6bfe2c58be` publishes the exact [web5-resolution-v1 contract](https://github.com/chung6a8m/MyDmsVn/blob/2d72700294227ef69f1a7a61a2969a6bfe2c58be/docs/contracts/web5-resolution-v1/README.md), consumed through `OperationResolutionPort`: separate `GET /api/v2/operations/context` and `GET /api/v2/operations/{operationId}/resolution`. The frontend pins 40 manifest-owned files and manifest SHA256 `fef5f1f18d3a556bf35d5c9ed6bc38af3eeb0c1a89dd5f9d125d7fb190a133b2`; field tables/errors belong to that contract, not duplicated here. **Do not change or fork WEB4's original 48 pinned JSON fixtures**. The selected additive design preserves the exact `web4-v1` context with no added fields (current decoder is strict), all six v1 mutation shapes and protected v1 status. New resolution/capability discovery uses a separate versioned surface. A negative must bind committed CANCELLED and matching immutable operator audit from one SQL transaction under the existing epoch/actor/key fence; absence or a generic administrator assertion cannot satisfy it.

Consumer must check:
1. Authenticated actor sourced from `/me`, current server epoch, **current grant for the original immutable operation kind from backend row** (Sales/Receipt Create/Update → Write; Sales/Receipt Post → Post), no stale actor generation and live session/document owner. **Do not require ordinary document Read for protected original-result status**: WEB4 W4-OP-12 allows Read denied/Write allowed. A new document Get/fresh editing baseline may require Read separately. Never use a caller-supplied kind or arbitrary persisted permissions to unlock.
2. Locally persisted frozen operation validates strictly; re-hash original byte-equivalent canonical command with the source-pinned WEB4 codec; match original operationId, command, route, HTTP method, target, expectedVersion, epoch, actor and checkpoint; reject a valid-looking certificate from a different request.
3. Typed server resolution and authenticated header must bind the exact operation, actor, database and fingerprint. Result must be a durable SQL terminal/positive fact, not a negative HTTP status or generic administrator remark.
4. Settle/local unlock **after** completed IndexedDB transaction and per-document CAS; if quota/versionchange/abort occurs after a response, retain UNKNOWN and offer local-only retry, not HTTP replay.
5. Late response after logout, changed actor/epoch, **revoked original Write/Post grant** (not merely general Read denial), close/dispose/tab split or editRevision change does not mutate the new document or Inventory query cache.

No JWT/refresh/cookie, SQL connection, operator credentials, raw business payload or server permissions are added to local persistence or telemetry. Local operator identifiers from corrupt records are display-only, explicitly unverified.

### 3.1 COMMITTED but missing original result — support closure is not edit recovery (P1-01)

`RESULT_EXPIRED` after the WEB4 seven-day readback window is not `NOT_EXECUTED`. The B03 operator may prove SQL business COMMITTED from journal/source/header/lines/stock/ledger/COGS, close a **support case**, and report `BUSINESS_COMMITTED_RESULT_UNAVAILABLE` with signed ticket/correlation, actor/epoch, time and protected authority. This is **not** the original Create/Update Write projection/version; the browser must not infer `SETTLED`, invent the missing result/rowversion, invoke public Get as operation proof, delete tombstones or retry with a new key. Keep that operation PROTECTED until an independently approved disposition. 

An optional local **case/draft archival** UI (only after an explicit Owner policy and F5-RES-13 tests) is user-confirmed, bound to exact current actor/epoch/key/fingerprint/CAS, retains minimal durable ticket/evidence and guarantees no mutation on archive. It may remove an item from the active workspace but not unlock the old operation for edit/another Post; it must preserve required user data and remain honest after IDB abort/quota/cross-tab conflict. For a different new document, require current authorized server read/version and explicit new user intent; Write-without-Read requires operator escalation. Show the seven-day deadline and human escalation state without inventing an automatic SLA.

### 3.4 Strict-cutover recovery of pre-existing WEB4 schema-v1 immutable intents (round-2 P1-01)

**Conditional reference only:** strict mode is not selected by ADR0015. F5-COMP-03/04 and F5-RES-14 are NOT_APPLICABLE under additive, not PASS or skipped required tests. A later strict decision restores every requirement below; common compatibility/recovery tests remain mandatory under additive.

**Do not strand existing `DISPATCHED/UNKNOWN` work when enabling strict mode.** Current `src/infrastructure/http/operationsContext.ts` requires `contractVersion: "web4-v1"`; `web4OperationCodec.ts` freezes `schemaVersion: 1`, original request/fingerprint, and `web4OperationRepository.ts` stores `schemaVersion: 1` states `DISPATCHED`, `SETTLED`, `REJECTED`. Those records are valid **legacy recovery inputs**, not new WEB5 mutation requests. The new frontend must establish authenticated actor and current database epoch under the accepted new operations context **without rejecting a recoverable old record merely because its frozen contract is v1**.

**Required F02 restore and local migration contract:**

1. Discover legacy v1 records under the **same authenticated actorKey + server-owned deploymentEpoch** after new context/capability resolution; validate local draft and `operations` checkpoint with existing strict v1 codec and recompute original **v1** SHA-256, not WEB5 canonical hash. Validate `operationId`, frozen operation kind/method/route/target/expectedVersion, local document/generation/editRevision and `DISPATCHED` ownership. Refuse unsupported/corrupt/foreign/stale records; show sanitized metadata only and retain the protected state. Do not rewrite raw edit buffers/clientLineIds/immutable request or transfer a record across actors/databases.
2. A new WEB5 frontend may **read** the original v1 outcome through B02's agreed read-only recovery route (either protected original v1 status or a new explicitly versioned recovery endpoint). Server verifies current actor/session/**the stored original operation-kind Write/Post grant**, epoch, ID and original requestFingerprint under the same SQL key fence; ordinary document Read denial **does not** block this status if original Write/Post is granted. Return only retained original command-specific `COMMITTED` details (Sales Post with version, Receipt Post without version). Strict mode rejects **all** old WEB4 `POST/PUT`; the read route never dispatches one. No automatic retry, new operation key or modified original payload.
3. If a matching COMMITTED outcome is returned, atomically persist the original authoritative settlement + draft checkpoint with per-document IndexedDB CAS and only then apply it to the current owned feature session. New local storage version/wrapper (if needed) must preserve the **v1 frozen bytes/digest and original operation lineage**, or reuse v1 schema safely; no migration may delete, replace, relabel `DISPATCHED` as `REJECTED` or discard the protected draft. IDB quota/versionchange/abort/two-tab conflict remains UNKNOWN with local-only retry.
4. `NOT_OBSERVED`/404 after serialization, still-in-flight, expired/unavailable original result, wrong actor/epoch/fingerprint, invalid/corrupt v1, **original Write/Post permission revoked**, `CANCELLED` or failed cross-version decoding must **stay locked**. **Ordinary Read denied alone is a positive case when the original Write/Post grant remains valid**, not grounds to lock a valid COMMITTED result. The v1 status route does not produce a new negative certificate; any terminal negative requires the separate reviewed B02 versioned operator contract. Seven-day expiry leads to positive operator reconciliation as applicable, not synthesized rollback or edit version.
5. Preserve the ability to load a protected draft **without requiring the old literal `web4-v1` operations-context response from the new backend**: negotiate current context first, then decode legacy frozen records through a deliberate versioned decoder. An old tab may request a legacy read under current authorization but cannot issue writes; after reload a new client can continue recovery. New client against old host fails safely without bypassing feature admission.

**If strict is later selected, F5-COMP-03/F5-COMP-04 and F5-RES-14 become mandatory:** in actual Chromium and Edge IndexedDB (not just a mock), seed a valid v1 pending snapshot before switch, deploy strict backend/new bundle and verify original COMMITTED readback, correct Sales/Receipt outcomes, retained raw data and no mutation count; include **positive denied ordinary Read + original Write/Post granted** and **negative revoked original Write/Post**, absent/in-flight/expired, invalid session, actor/epoch change, invalid fingerprint, app restart and IDB failures. B04-B separately proves original SQL outcome and no legacy mutation; F04/B05 repeat the paired full IIS scenario. If legacy recovery readback is missing, mark strict cutover BLOCKED and leave UNKNOWN locked.

## 4. User experience and accessibility

**Historical F02 fallback checkpoint (2026-11-02):** [Task evidence](../evidence/web5/20261102-f02-operator-metadata.md) records the bounded read-only support metadata UI when B02/B04-B were absent. It exposes only sanitized operation/epoch/correlation or quarantined primary-key UUIDs, explicitly unverified; correlation is a lookup aid, not a created support ticket. Corrupt/unknown-kind metadata is conservatively hidden unless both current Write and Post remain allowed; a validated original operation uses its exact Write/Post grant without ordinary Read. Active metadata is fenced by actor/epoch/generation/edit revision and current grant. Unsupported raw values and unresolved business previews are never support content. That fallback candidate added no backend resolution/certificate, ticket closure, archival or unlock.

The fallback derives local retry eligibility from the existing runtime's cached original proof/rejection. When eligible, the dialog exposes **Thử lại lưu cục bộ** with no HTTP fallback; otherwise it exposes **Kiểm tra kết quả** using existing protected v1 GET. Reload loses the in-memory proof and requires a new explicit status check. Both **Gửi lại đúng thao tác** and **Mở khóa thao tác** remain disabled with an accessible reason. Identifier copy is user-triggered and rechecks admission; if clipboard access fails, identifiers remain selectable. Base UI owns modal focus/dismiss and returns focus to the opening control. Full F02 was BLOCKED at that fallback checkpoint. The implemented terminal flow below now has its own source and evidence; it does not retroactively change the fallback result.


### 4.1 Current terminal-resolution workflow

Current source adds an explicit local NOT_EXECUTED operation-record version2 while preserving the frozen v1 request and the existing IndexedDB stores. A shape-valid stored certificate is not authority: restoration of a clean negative draft requires a new authenticated exact decision read, a final exact draft reread and synchronous adoption admission. A current unresolved operation restores locally under its own original grant and remains protected until an explicit result check. Runtime-only lineage admission binds current scope/original grant; it is invalidated on revoke and before an explicit decision recheck. Any failed recheck, including 403 with stale local capability data or timeout, keeps review/editing protection until complete fresh success. Native transaction failure retains UNKNOWN and cached-proof retry never falls back to HTTP.

User workflow (implemented and verified within the bounded nonproduction scope; hosted CI/merge disposition remains separate):

1. Khi kết quả ghi chưa rõ, giữ trang/bản nháp. Mở **Đối soát thao tác**. **Kiểm tra kết quả** đọc kết quả gốc theo hợp đồng cũ; **Kiểm tra xử lý hỗ trợ** yêu cầu quyết định theo hợp đồng mới. Cả hai đều là thao tác đọc do người dùng chọn, không gửi lại Save/Post. Host cũ không có phần mở rộng chỉ có thể tiếp tục đọc kết quả dương gốc; không tạo xác nhận âm.
2. Nếu đã có kết quả nhưng chưa lưu được trên thiết bị, chọn **Thử lại lưu cục bộ**. Thao tác này chỉ thử lưu bằng chứng đang có trong phiên; không gửi HTTP. Sau tải lại mất cache trong bộ nhớ, phải kiểm tra lại với máy chủ. Không xóa dữ liệu trình duyệt khi còn UNKNOWN.
3. Chỉ sau khi máy chủ xác nhận chính xác thao tác gốc không thực hiện và IndexedDB hoàn tất CAS, bản nháp mới chuyển sang bước review. Nội dung/raw/lookup/clientLineId được giữ. Quyết định đã lưu sau tải lại phải được xác minh mới; **Xác minh lại quyết định** không tự mở quyền ghi nếu phản hồi bị từ chối hoặc không xác định.
4. Với chứng từ mới chưa có ID máy chủ: xem lại nội dung được giữ, chọn ô đồng ý và **Xác nhận giữ nội dung và tạo ý định mới**. Sau đó đóng hộp thoại và chọn **Lưu chứng từ/Lưu phiếu nhập** riêng. Lần lưu dùng UUID mới; việc xác nhận không gửi yêu cầu ghi và không gửi lại UUID gốc.
5. Với chứng từ đã có ID: đóng hộp thoại, chọn **Đọc lại để review**, xem bản máy chủ hiện tại rồi **Xác nhận bỏ bản sửa và dùng bản đọc**. Chỉ bước xác nhận này chấp nhận bản đọc thay nội dung đang giữ. Bước đọc baseline cần quyền Read hiện tại; quyền Write/Post cho phép đọc kết quả gốc nhưng không thay quyền Read. Nếu Read bị từ chối, giữ bản nháp và liên hệ người phụ trách; không tạo lại hoặc Post lại.
6. Nếu đã xác minh thao tác cũ không thực hiện rồi bắt đầu một thao tác mới, đối soát thao tác mới dùng đúng quyền Write/Post gốc của thao tác mới, kể cả khi Read bị từ chối hoặc quyền khác của thao tác cũ đã bị thu hồi. Khi thao tác mới còn UNKNOWN, không hiển thị mã/quyết định của thao tác cũ. Kết quả dương mới chỉ hoàn tất thao tác mới; lịch sử xác nhận âm vẫn được giữ và tiếp tục bảo vệ sửa/xóa nếu chưa đủ quyền hoặc chưa xác minh mới.
7. 404, 403, timeout, INDETERMINATE và kết quả hết hạn/không dùng được không chứng minh rollback. Giữ khóa, dùng mã thao tác/cơ sở dữ liệu/mã tương quan an toàn để nhờ hỗ trợ. Mã tương quan không phải xác nhận đã tạo/đóng phiếu hỗ trợ. Chưa có chức năng gửi lại đúng thao tác hoặc ẩn hồ sơ đối soát; không xóa bản nháp để thay thế. Không có phê duyệt production.

Keep Nova/Base UI theme, typography and standard compactness unchanged. Use three visually distinct actions:
- **Kiểm tra kết quả:** protected GET only, permitted only with current session and the original operation's Write/Post grant (ordinary Read is not required); negative/unavailable stays locked.
- **Thử lại lưu cục bộ:** retry IndexedDB, never HTTP.
- **Gửi lại đúng thao tác:** conditional manual same-key HTTP (disabled until gates accepted); show exact original command/ID, prompt explicit confirmation, status check and one dispatch; never default or enter-key automatic submission.

For safely verified terminal-negative:
- Label clearly "Máy chủ đã xác nhận thao tác gốc không được thực hiện" only with durable certificate.
- Preserve draft/keyboard focus and allow reviewing newer baseline; new Save/Post remains disabled until the current valid state is verified, permissions refreshed and user consciously starts a new intent.
- Warn when result was COMMITTED but expired: business may exist; never invite re-Post or clear a protected journal marker.
- In cross-tab conflicts show both owners and preserve raw/local information without choosing newer by timestamp. No automatic clearing of a different tab.

Test accessibility in real browser with AG Grid, Dockview and Floating UI active: tab sequence, focus trapped/restored around modal, live-region status announced once without duplicated alerts, keyboard-only review, screen reader/Narrator on attended Windows and Telex/VNI composition. Synthetic composition does not certify human IME.
